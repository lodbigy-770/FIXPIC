## שלב 0 – קליטת מודל ומחקר (קדם-תנאי ל-M1)

**תלות:** הורדת המודל ע"י המשתמש (אין גישה ל-Hugging Face מסביבת העבודה).

**סטטוס (2026-11-11):** בוצע בעיקרו ע"י KIRO (קומיטים `9923eb3`, `94d3064`): נבנתה חבילת `stage0_validation/` עם נקודת כניסה `validate_stage0.py`, וההרצה נעשתה אצל המשתמש על הקובץ האמיתי. **אושר ע"י פלט ההרצה שהמשתמש הדביק** (קוד יציאה 0, SHA256 וגודל תואמים, לא pointer, session נטען; פרטים ב-`DEVELOPMENT_LOG.md`). בסביבת Claude הקובץ נשאר LFS pointer (הרשת חוסמת את `github-cloud.githubusercontent.com`), ולכן ההרצה לא שוחזרה כאן. הטווח 64–4096 עדיין לא אומת.

**מטרות:** להכניס את קבצי המודל לריפו ולאפיין אותו על בסיס הקבצים בפועל.

**משימות**
- [~] בדיקת מבנה הריפו ב-HF; זיהוי קובץ ה-ONNX וקבצי עזר (config, metadata, external data). זוהה `inpainter.onnx` מול הקובץ בפועל; מבנה הריפו ב-HF עצמו לא נבדק (אין גישה מסביבת העבודה).
- [x] הורדת קבצים נחוצים בלבד אל `models/big-lama/` (ONNX דרך LFS, README, LICENSE).
- [~] תיעוד: Revision/Commit, שמות, גדלים, SHA256, רישיון (`models/big-lama/README.md`). שמות, גדלים, SHA256 ורישיון מתועדים ב-`MODEL_CARD.md`; Revision/Commit ב-HF חסר.
- [x] בדיקת Git LFS ואימות שאין קבצי pointer (`FileValidator`; הורצה אצל המשתמש, KIRO2).
- [x] אפיון שמות, תפקידים ומידות של Input/Mask/Output Tensors (`ModelInspector`; הורץ אצל המשתמש).
- [x] אפיון Padding, נרמול וזיכרון בפועל (בוצע ב-M1: ריפוד נבדק על 534×800 ו-800×534, שיא זיכרון כ-1.27GB).

**תוצרים:** `models/big-lama/*`, `MODEL_CARD.md` מלא.
**בדיקות:** SHA256 תואם; `onnxruntime.InferenceSession` נטען; גודל קובץ תואם לצפוי.

## Milestone 1 – Model Integration

**משימות**
- [x] טעינת Big LaMa ב-ONNX Runtime CPU (`probe`: 2.51 שניות, `CPUExecutionProvider`, onnxruntime 1.31.1).
- [x] הדפסת מטא-דאטה של Inputs/Outputs (בוצע ע"י `m1_check.py probe`, כל הבדיקות PASS; `tools/poc/probe_and_run.py` לא הורץ).
- [x] בדיקת תמונת קלט + מסכה → תמונת פלט (סינתטי 640×480 ושלוש דוגמאות אמיתיות).
- [x] אותה בדיקה על תמונות אמיתיות וגם על גודל שאינו כפולה של 8 (534×800 ו-800×534; הריפוד נבדק).
- [x] בדיקת תקינות: גודל פלט, טווח ערכים, פיקסלים מחוץ למסכה אחרי מיזוג (סינתטי, 640×480; הפלט הגולמי מחוץ למסכה זהה למקור ב-0 רמות).
- [x] מדידת זמן וזיכרון בסיסית (ברירת מחדל של threads, מחשב עם 4 ליבות, Windows 11: סינתטי 640×480 כ-5.1–5.8 שניות; אמיתי כ-0.43MP בין 6.6 ל-9.7 שניות; שיא זיכרון 1.27GB).

**תוצרים:** PoC עובד, תוצאות מדידה ב-`DEVELOPMENT_LOG.md`, השלמת `MODEL_CARD.md`.
**בדיקות:** 3 תמונות בדיקה (הסרת אדם / טקסט / שריטה) – בדיקה ויזואלית; בדיקה אוטומטית שפיקסלים מחוץ למסכה זהים למקור.
**DoD:** PoC רץ מקצה לקצה ב-CPU בלי GPU וללא רשת; התוצאה תועדה.

## Milestone 1.5 (שלב ביניים) – Latency Spike והחלטת Runtime/Stack

**תלות:** M1.
**מטרות:** לבדוק אם לולאת "משיכה → תוצאה" ריאלית ב-CPU, ולהכריע ADR-002.

**סטטוס (2026-11-12): בוצע ונסגר.** המדידות בוצעו אצל המשתמש (i5-6500T, 4 ליבות פיזיות, 7.9GB, ORT 1.31.1, OpenVINO 2026.4.1, Python 3.14.3) ונותחו; הפירוט ב-`DEVELOPMENT_LOG.md` ובטבלה ב-`MODEL_CARD.md` §6. הוכרעו: תקציב Latency, Python 3.14, OpenVINO ראשי עם ORT fallback (ADR-011), 3 threads, ללא GPU, ללא מטמון compile כברירת מחדל, ללא רכיב נייטיב, ופירמידת הקטנות לתצוגה. **לא נבדק:** אימות אריזה על 3.14 (PyInstaller/Nuitka עם PySide6, OpenVINO, ORT, OpenCV) הועבר ל-M5 לפי בחירת המשתמש.

**משימות**
- [x] **Latency Spike:** מדידת זמן Inference עבור ROI בגדלים 128–1024; גם Warm וגם Cold. (בוצע 2026-11-12: Cold קרוב ל-Warm; 256→0.83s, 384→1.94s, 512→3.79s, 768→9.73s, 1024→17.89s ב-4 threads.)
- [x] מדידת התלות במספר ה-Threads. נמדדו 1/2/3/4 (המחשב בן 4 ליבות פיזיות, ולכן 8 לא רלוונטי). 2→4 threads משפר רק פי 1.2–1.4. **3 threads** עולה רק 3–8% ב-ORT ו-14–20% ב-OpenVINO לעומת 4, ומשאיר ליבה ל-UI.
- [x] השוואת ONNX Runtime CPU ל-OpenVINO (בוצע 2026-11-12, `openvino_results.json`): OpenVINO CPU מהיר מ-ORT ב-10–30% באותו מספר threads, ו-OpenVINO ב-3 threads שווה או מהיר מ-ORT ב-4 (0.83/1.68/3.12 שניות לקלט 256/384/512). עלות: compile של 5.4–5.8 שניות לכל גודל. ה-iGPU לא נותן יתרון ונפסל. **אומץ כ-backend ראשי עם ORT כ-fallback (ADR-011), אושר במפורש ע"י המשתמש 2026-11-12.** צורה דינמית (`openvino_dynamic.json`): compile אחד של 5.1 שניות לכל הגדלים, ו-Latency דומה לסטטי (256: 0.94 מול 0.81, 384: 1.72 מול 1.85, 512: 3.14 מול 3.27 שניות). (פירוט בהמשך השורה על הכלי:) נבדק ב-PyPI: חבילת `openvino` 2026.4.1 כוללת גלגל cp314 ל-Windows x64; `onnxruntime-openvino` נעצר ב-3.13, ולכן הכלי משתמש ב-API הנייטיב של OpenVINO. הכלי מודד גם 3 threads (מול 4) ו-iGPU של Intel (אופציונלי, `--devices CPU GPU`).
- [x] מדידת עלות Pre/Post בנפרד מה-Inference. Pre+Post הוא עד כ-80ms ב-1024 (פחות מ-0.5%), Resize 1536↔512 הוא 2–17ms.
- [x] קביעת תקציב Latency סופי למשיכה טיפוסית. אושר ע"י המשתמש 2026-11-12; עודכנו `PLAN.md` §3 ו-`PARITY-SPEC.md` §3/§6.
- [x] אימות Python: זמן Pre/Post ב-NumPy/OpenCV על ROI, זמן עלייה של האפליקציה, ושחרור ה-GIL בזמן `run` (ה-UI נשאר רספונסיבי). בוצע 2026-11-12 (`gil_startup.json`): ב-384 עם 3 threads, האיחור המרבי של ה-thread הראשי בזמן inference זהה ל-baseline (כ-43ms ב-OpenVINO, 16ms ב-ORT, מול 2 שניות של inference), ועבודת Python טהורה נשארת ב-98–100%. זמני import: openvino 0.96, onnxruntime 0.55, cv2 0.41, numpy 0.34, PySide6.QtWidgets 0.33, המנוע 0.49 שניות. מדידת אריזה בפועל נשארת (ADR-002).
- [x] UI Spike: Zoom/Pan חלק על תמונה של 24MP ב-PySide6 (פירמידת הקטנות/Tiles לתצוגה). בוצע 2026-11-12: הפירמידה (רמות 1/2^k, ציור של המלבן הנראה בלבד) הורצה אצל המשתמש ב-`ui_spike.py --interactive` ונמצאה מהירה וטובה לשימוש. לא נדרשים Tiles ל-24MP. לא נמסרה טבלת benchmark מהמחשב היעד.
- [x] הכרעה אם נדרש רכיב נייטיב (Cython/C++) מחוץ ל-Inference: **לא נדרש.** Pre/Post/Resize זניחים, ה-GIL משוחרר בזמן `run`, וזמן ה-import כ-1.5–2 שניות אינו עניין לנייטיב. הכרעה זו נשענת על מדידה מבודדת בלי Qt; ה-UI Spike יאשר אותה עם לולאת אירועים אמיתית.

**תוצרים:** טבלת מדידות, ADR מעודכן, תקציב Latency מוסכם.
**DoD:** החלטה מתועדת עם נתונים. אם ה-Latency גבוה מכדי חוויה אינטראקטיבית – מתועדות חלופות (OpenVINO, Quantization, ROI קטן יותר, מצב "הרץ" ידני) לפני המשך.

## Milestone 2 – Core Inpainting Engine

**תלות:** M1 (ו-M1.5).
**מטרות:** מנוע עצמאי (ספרייה ללא UI).

**סטטוס (2026-11-13): בוצע (שיחה B), על מודל סינתטי.** בוצעו M2.1–M2.9 (160 בדיקות עוברות; `tests/test_real_model.py` ובדיקת איכות/זמנים על Big LaMa רצים אצל המשתמש). הערכים הזמניים של M2.4/M2.8 (ספי קיבוץ, יחס הרחבה, הקשר מצומצם) ממתינים להשוואת איכות על תמונות אמיתיות.

**משימות**
- [x] `InpaintModel` + מימוש ONNX (M2.1); backend OpenVINO ראשי עם fallback אוטומטי ל-ORT ו-Warm-up (M2.2).
- [x] Model Manager (טעינה, מטא-דאטה, בדיקת hash) (M2.3).
- [x] Pipeline: ROI, Pad/Resize, Pre/Post, מיזוג (M2.1); Feathering פנימי ב-M2.4.
- [x] Tiling עם חפיפה לתמונות/מסכות גדולות, וקיבוץ מסכות מרובות/רחוקות (M2.4; ספי החלטה זמניים).
- [x] ניהול זיכרון: תקרה (הערכה מראש), התאוששות מ-OOM, מיזוג בפסים (M2.5). שימוש חוזר בבאפרים נבדק ונדחה: הבאפרים בגודל חלון (עד 1MB בקלט S×S), לא המקור לזיכרון.
- [x] ביטול (`CancelToken`, M2.1) ודיווח התקדמות (`progress=`, M2.5).
- [x] **M2.6** Job Scheduler (`engine/scheduler.py`): תור FIFO (עד 3 ממתינות), Worker יחיד, Warm-up ברקע bucket-אחר-bucket (עבודה בתור קודמת ל-bucket הבא), ביטול עבודה ממתינה/רצה ו-`cancel_all` ל-Undo (ARCHITECTURE §4א). המודל נקרא פעם אחת (`read_model` ב-`load`, `clone` לכל צורה).
- [x] **M2.7** CLI לבדיקה (`python -m fixpic`, עובר דרך ה-Scheduler) ובדיקות 1MP / 12MP / 24MP, מסכות קטנות/דקות/גדולות/מרובות/ריקה, מודל פגום, ביטול באמצע (`tests/test_m27.py`). **על מודל סינתטי בלבד**; הרצה על Big LaMa האמיתי נשארת אצל המשתמש.
- [x] **M2.8** הרחבת מסכה אוטומטית יחסית לגודל המברשת (ADR-008; `pipeline/dilate.py`, `brush_px` מה-UI או הערכה מהמסכה) ו"רזולוציה מקורית תחילה" (ARCHITECTURE §4ב: צמצום הקשר עד 10% לפני הקטנה). **הערכים זמניים; איכות לא נמדדה** (נדרש Big LaMa אמיתי).
- [x] **M2.9** טיפול בשגיאות לפי ARCHITECTURE §10 ובדיקת ה-DoD של M2 כולו. נסקרו שש שורות הטבלה מול המימוש ונסגרו שלושה פערים: (1) `Pipeline.run` הוא עכשיו גבול ה-Engine: רק `FixPicError` יוצא (חריגה לא צפויה → `InferenceError`, חריגת זיכרון → `OutOfMemoryError`), וקלט שאינו ndarray או תמונה ריקה → `InvalidInputError`; (2) `AutoModel`: כשל גם ב-fallback משאיר מצב מוגדר (ללא backend פעיל, ללא לולאת ניסיונות); (3) כשל טעינה/hash נרשם ביומן וחוסם Inpaint. `tests/test_m29.py` (25 בדיקות, שורה-לשורה + רצף כשלים ועבודות תקינות על Worker יחיד). **DoD אומת על מודל סינתטי בלבד**; הרצה על Big LaMa אמיתי נשארת אצל המשתמש.

**תוצרים:** ספריית Engine + בדיקות יחידה + CLI לבדיקה.
**בדיקות:** תמונות 1MP / 12MP / 24MP; מסכות קטנות/גדולות/מרובות; מסכה ריקה; קובץ מודל פגום; ביטול באמצע.
**DoD:** אין קריסות על סט הבדיקות; פיקסלים מחוץ למסכה זהים; שימוש בזיכרון מתחת לתקרה שהוגדרה.

## Milestone 3 – Editing Interface

**תלות:** M2.
**מטרות:** אפליקציית PySide6 בסיסית שמשתמשת במנוע.

**פירוק לשלבי ביצוע** (שלב אחד בכל פעם; הסימון בפועל נעשה במשימות שמתחת):
- **M3.1 – ניהול תמונות (ללא UI): בוצע (2026-11-13).** `fixpic/imgio`: טעינה/שמירה PNG/JPG/WebP, נתיבי Unicode, Alpha, EXIF/ICC, שמירה אטומית, `image_from_array` להדבקה.
- **M3.2 – שירותי אפליקציה (ללא UI): בוצע (2026-11-13).** `fixpic/session` (`Session`: תמונה עובדת, Commit אטומי מתוצאת Job לפי מסכה, `submit_stroke`/`finish`, Undo/Redo; `MaskLayer`: ציור/מחיקה על מסכה בגודל התמונה; `alpha.py`: מדיניות Alpha) ו-`fixpic/history` (`History`, `Patch`: מגבלת צעדים וזיכרון). Undo בזמן Processing = ביטול כל ה-Jobs. `tests/test_m32.py`, 65 בדיקות.
- **M3.3 – שלד ממשק:** `strings/he.json` וטעינתו, `QApplication` ב-RTL, חלון ראשי, Canvas (`QGraphicsView`) עם Zoom/Pan על פירמידת הקטנות (לפי M1.5), פתיחה/גרירה/הדבקה, שמירה/ייצוא ברקע עם התקדמות.
