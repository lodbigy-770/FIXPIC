# ARCHITECTURE – מערכת Cleanup AI (Offline, CPU)

> עודכן: 2026-11-10. סימון: **[אומת]** / **[לא אומת]** כמו ב-`PLAN.md`.
> מסמך זה הוא תכנון. טרם מומש קוד מוצר.

## 1. עקרונות מנחים

- פשטות, מקומיות, קלות תחזוקה.
- הפרדה מלאה בין UI, מנוע עיבוד ומודל.
- המודל הוא "תוסף" מאחורי ממשק קבוע (`IInpaintModel`), כך שאפשר להחליף אותו.
- אפס תלות ברשת, GPU או CUDA.
- כל החלטה משמעותית מתועדת כ-ADR בסעיף 12.

## 4. Pipeline מלא (תכנון)

1. **קלט**: תמונה מקורית (RGB 8-bit) + מסכה בינארית (0/255) באותו גודל.
2. **נרמול מסכה**: סף, הרחבה (dilate) קלה אופציונלית (ברירת מחדל מוצעת: מספר פיקסלים בודדים) כדי לכסות שוליים חצי-שקופים.
3. **חישוב ROI**: מלבן תוחם של המסכה + שולי הקשר (context margin) סביבה. מעבדים רק את ה-ROI, לא את כל התמונה.
4. **החלטת אסטרטגיה** לפי גודל ה-ROI מול גודל הקלט הנתמך של המודל:
   - ROI קטן/שווה לקלט המודל: Padding לגודל הנדרש.
   - ROI גדול: Resize ירידה (עם שמירת יחס) *או* Tiling עם חפיפה – תלוי באיכות הנמדדת (ראו הערה בסעיף 8).
5. **Preprocessing**: המרה ל-float32, נרמול, סידור ממדים (NCHW) – **הפרטים המדויקים [לא אומתו]** ויילקחו מהמודל בפועל.
6. **Inference**: `session.Run` ב-CPU.
7. **Postprocessing**: דה-נרמול, חזרה ל-uint8, חיתוך ה-Padding, Resize חזרה לגודל ה-ROI.
8. **מיזוג**: `out = orig * (1 - m) + result * m`, כאשר `m` היא המסכה אחרי Feathering. פיקסלים עם `m = 0` נשארים זהים למקור.
9. **פלט**: תמונה חדשה בגודל המקורי + תיעוד (Δ) להיסטוריה.

## 5. ניהול תמונות ומסכות

- תמונה פנימית: Mat/Buffer בפורמט BGR או RGB אחיד (החלטה אחת בכל המערכת, מתועדת).
- מסכה: ערוץ יחיד uint8, גודל זהה לתמונה. ערכים: `255` = להסרה, `0` = לשמירה. **[זו מוסכמת המערכת; המוסכמה של המודל לא אומתה]** – תבוצע המרה ב-Preprocessing.
- ציור מסכה: Layer נפרד מעל התמונה, לא משנה את התמונה עד הרצה.
- תמונות עם ערוץ Alpha: ה-Alpha נשמר בנפרד וממוזג חזרה (המודל מקבל RGB).
- ICC/EXIF: נשמרים בשמירה כשהפורמט תומך בכך.

## 6. תקשורת עם ONNX Runtime

- Session אחד לכל מודל טעון, נוצר פעם אחת ומשמש שוב (יצירה יקרה).
- אפשרויות Session (להתחיל מברירות מחדל ולמדוד): `IntraOpNumThreads` לפי ליבות פיזיות, `GraphOptimizationLevel = ORT_ENABLE_ALL`, `ExecutionMode = Sequential`.
- שמות Input/Output **נקראים מהמודל בזמן טעינה** (`session.InputMetadata`), לא קבועים בקוד.
- ללא `Providers` שאינם CPU. אין חבילות CUDA/DirectML.
- אופציה עתידית: OpenVINO EP (Intel) מאחורי אותו `IInpaintModel`, מוכרע ב-M1.5 לפי מדידות.

## 7. ניהול זיכרון ועיבוד CPU

- עיבוד ב-ROI בלבד, לא על כל התמונה.
- Tiles מעובדים **טורית** (לא במקביל) כדי לא להכפיל צריכת זיכרון; המקביליות מגיעה מתוך ONNX Runtime (intra-op threads).
- שימוש חוזר בבאפרים (Tensor Pool) בין Tiles.
- תקרת זיכרון מוגדרת; חריגה צפויה → הקטנת Tile / הורדת רזולוציית עיבוד עם מיזוג חוזר.
- ריצה ברקע (Thread נפרד) עם `CancellationToken` ו-Progress.
- תמונה מקורית בגודל מלא נשמרת ב-RAM פעם אחת; היסטוריה שומרת **רק Δ של ה-ROI** (ראו סעיף 9).

## 8. תמיכה בתמונות גדולות

**[הנחה, לא אומתה]**: מודלי LaMa מיוצאים ל-ONNX לעיתים עם קלט בגודל קבוע; ייתכן שהמודל הזה קבוע. אם כך נדרש Crop/Pad/Tiling. ההחלטה הסופית תלויה בבדיקת הקובץ בפועל.

אסטרטגיית ברירת מחדל מוצעת:

1. **Crop סביב המסכה** (ROI + הקשר). אם ה-ROI נכנס בגודל המודל – הרצה אחת.
2. ROI גדול מעט: Resize ירידה → הרצה → Resize עלייה → מיזוג רק בתוך המסכה. (איכות מופחתת בטקסטורות; מתועד כמגבלה.)
3. ROI גדול מאוד (מסכה רחבה): Tiling עם חפיפה, ריצה טורית, מיזוג Feathered בין Tiles. אזורים שנוצרו בקריאה קודמת משמשים כהקשר לבאים אחריהם.
4. חלוקה למסכות נפרדות (Connected Components) – כל רכיב מסכה מעובד ב-ROI משלו (תומך F9).

## 9. מנגנון Undo/Redo

- תבנית **Command** עם שני מחסנים (undo / redo).
- פעולות הניתנות לביטול: שינוי מסכה (Stroke), הרצת Inpainting, טעינה מחדש.
- Inpainting נשמר כ-**Patch**: מלבן ROI + פיקסלים לפני + פיקסלים אחרי (דחוס). כך Undo לא דורש שמירת תמונה מלאה בכל צעד.
- מגבלת היסטוריה: לפי מספר צעדים *ולפי* תקרת זיכרון (הקטן מביניהם); גלישה מוחקת את הישנים ביותר.
- Redo מתאפס בכל פעולה חדשה.

## 10. טיפול בשגיאות

| מצב | טיפול |
|-----|-------|
| קובץ מודל חסר / hash לא תואם | הודעה ברורה, חסימת Inpaint, תיעוד ביומן |
| OOM / הקצאה נכשלה | ניסיון חוזר ב-Tile קטן יותר; אם נכשל – הודעה למשתמש, התמונה לא משתנה |
| חריגה ב-ONNX Runtime | נתפסת בשכבת Engine, מומרת לשגיאה מוגדרת; מצב האפליקציה נשמר |
| מסכה ריקה | הודעת "לא סומן אזור", ללא הרצה |
| ביטול ע"י משתמש | `CancellationToken`, ללא שינוי בתמונה |
| תמונה פגומה / פורמט לא נתמך | הודעה, ללא קריסה |

עקרון: **פעולה נכשלת לעולם לא משנה את התמונה הנוכחית** (Commit אטומי רק בסיום מוצלח).

## 11. החלפת מודל בעתיד

ממשק מוצע (פסאודו-קוד):

```
interface IInpaintModel {
    ModelInfo Info { get; }          // שם, גרסה, רישיון, גדלי קלט נתמכים
    void Load(ModelConfig cfg);
    InpaintOutput Run(Tensor image, Tensor mask, CancellationToken ct);
    void Unload();
}
```

- כל מודל מגיע עם `model.json` (מטא-דאטה) בתיקייה משלו: `models/<name>/`.
- ה-Pipeline מקבל מה-`ModelInfo` את: גודל קלט, סוג נרמול, מוסכמת מסכה, צורך ב-Padding. כך החלפת מודל לא משנה את הפיפליין.
- מודל חדש = תיקייה חדשה + מימוש/הגדרה; ללא שינוי ב-UI.

## 12. החלטות ארכיטקטוניות (ADR)

### ADR-001 – ONNX Runtime CPU כמריץ ראשי
- **החלטה:** ONNX Runtime CPU EP.
- **סיבה:** פורמט המודל הנבחר הוא ONNX; Runtime בוגר, Offline, ללא GPU.
- **חלופות:** OpenVINO (נבחן ב-M1.5 כהאצה ל-Intel); PyTorch (כבד, לא נדרש).
- **סטטוס:** מאושר.

### ADR-002 – Stack: C# / WPF לממשק; מנוע – להכרעה
- **החלטה זמנית:** WPF ל-UI; מנוע עיבוד ב-C# עם OpenCvSharp (או EmguCV) + `Microsoft.ML.OnnxRuntime`.
- **סיבה:** פשטות פיתוח, חבילת NuGet אחת למריץ, פחות שכבות Interop.
- **חלופה:** ליבת C++ (DLL) – רק אם המדידות ב-M1.5 מראות צוואר בקבוק בעיבוד התמונה (לא ב-Inference).
- **סטטוס:** זמני, מוכרע ב-M1.5.

### ADR-003 – עיבוד ROI ולא תמונה מלאה
- **החלטה:** Crop סביב המסכה עם הקשר, מיזוג חוזר רק בתוך המסכה.
- **סיבה:** חוסך זמן וזיכרון, ומבטיח שפיקסלים מחוץ למסכה אינם משתנים.
- **סטטוס:** מאושר.

### ADR-004 – Undo כ-Patch
- **החלטה:** שמירת Δ של ROI ולא תמונה מלאה.
- **סיבה:** זיכרון.
- **סטטוס:** מאושר.

### ADR-005 – שמות Tensors ופרמטרי קלט נקראים מהמודל
- **החלטה:** אין קידוד קשיח; נקרא מ-`session` + `model.json`.
- **סיבה:** דרישת המשתמש לא להניח, והחלפת מודל קלה.
- **סטטוס:** מאושר.
